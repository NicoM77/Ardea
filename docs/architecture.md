# Architecture

A map of how Ardea is built: the shape of the program, its modules, the rules between them and how work flows
through them. The reasons are in the [architecture decision records](adr/README.md). Three pages go deeper:

- [Data model](architecture/data-model.md): the schemas, the main tables and how they relate.
- [Rule set and levels](architecture/rule-set.md): how a vulnerability becomes a finding with a priority, a reminder
  or a notice.
- [Security model](security/security-model.md): sign-in, roles, tenant isolation, secrets and outbound connections.

## Shape

- **A modular monolith with a separate worker.** One program in one container image, started in one of three
  roles: `api` (the HTTP endpoints, the [OpenAPI document](../openapi/ardea.v1.json) and the web app), `worker`
  (the jobs: fetching sources, assessing, notifying) and `migrate` (database migrations, with a dump before them,
  [ADR 028](adr/0028-runtime-image-and-pre-migration-dump.md)). Both lasting roles load the same modules and
  differ only in what they start.
- **PostgreSQL 18.** Each module owns its own database schema and `DbContext`. Tenant isolation is an access check
  and a query filter, with row-level security as hardening ([ADR 029](adr/0029-row-level-security-as-hardening.md)).
- **Jobs in the database.** A job table read with `SKIP LOCKED` runs the scheduled and follow-up work and serves as
  the outbox; one unit of work spans every module a job touches.
- **The web app** (`web/`) is an Angular application with its own component library, built into the image and
  served by `api`.

The worker does the work that talks to the outside: the vulnerability sources, GitHub, the optional language model,
and SMTP, push services and webhooks for notifications. `api` calls out only while a person waits for it, for example
for a connection test or a repository search. The browser talks only to `api`.

### Technology

.NET 10 with ASP.NET Core minimal APIs and ASP.NET Core Identity; EF Core with Npgsql on PostgreSQL 18; Cronos for
schedules; MailKit for e-mail; Microsoft.Extensions.AI for language models (OpenAI-compatible endpoints, Ollama,
Anthropic); OpenTelemetry. The web app is Angular 22 (standalone components, signals, no zone.js) on the Angular CDK,
with Transloco for translations and an API client generated by orval from the OpenAPI document. The image is based on
`aspnet:10.0-noble-chiseled-extra`: no shell, no package manager, not root.

### Hosts and commands

`src/Hosts/Ardea.Host` is the one program. Besides the three roles it has helpers for the container and the
operator: `healthcheck`, `init-env`, `doctor`, `version`, the maintenance commands (`admin`, `intel`, `assess`,
`catalog`, `org`) and `seed-demo`. `ardea help` lists them; [Operation](operations/operations.md#maintenance-commands)
explains them.

API and worker start only when the database schema is at least at the level of their build; a newer schema that was
extended compatibly is allowed. `migrate` applies the modules' migrations in a fixed order (`platform`, `iam`,
`catalog`, `assets`, `intel`, `assess`, `notify`) and then loads the master data: sources, catalogue and rule set.

## Rules between modules

1. A module uses another only through that module's `Contracts` assembly: query interfaces, data transfer objects
   and subscriber interfaces. Everything else is `internal`; only the module's entry point (`*Module`) is public.
2. No module reads or writes the tables of another module.
3. Dependencies point one way: Catalog and Iam use no other module; Intel uses Catalog; Assets uses Catalog and
   Iam; Assessment uses Intel, Assets, Catalog and Iam; Notifications uses Assessment, Iam and Intel. Cycles are not
   allowed. A contract that writes another module's data is an exception and needs an ADR; the only one is
   `IProfilePlacement`, through which an answer on the Notices page places a component in the profile
   ([ADR 047](adr/0047-notice-generation-and-answers.md)).
4. Source adapters know only the provider SDK: no database, no tenant data, no other adapter.
5. `Contracts` assemblies reference only the shared kernel; the platform and the shared kernel know no module.

Architecture tests in the build (`tests/Ardea.Architecture.Tests`) enforce these rules. The rules for code,
dependencies and tests are in [`CONTRIBUTING.md`](../CONTRIBUTING.md).

### Inside a module

A module is two projects: `Ardea.<Module>` and `Ardea.<Module>.Contracts`. The module project is organised in folders
by concern, such as `Features` (endpoints and their handlers), `Persistence` (the `DbContext`, its configuration
and migrations) and folders for the module's jobs and domain rules. The `*Module`
class registers the services, endpoints, jobs and database. Endpoints call plain handler classes directly; there is
no mediator and no object mapper. Domain rules do not depend on EF Core, HTTP or the clock.

## How modules talk

- **Queries.** The owning module implements the query interfaces of its `Contracts`, for example `IEntryQueries`
  (Intel), `IProfileQueries` (Assets), `IOrganizationMembers` (Iam) or `IActionFacts` (Assessment).
- **Changes.** A module announces a change through a subscriber interface in its `Contracts`
  (`IEntryChangeSubscriber`, `IProfileChangeSubscriber`, `IActionEventSubscriber`, `ICatalogChangeSubscriber`,
  `IOrganizationCreatedSubscriber`, …). Subscribers run in the same unit of work as the change and usually only
  queue a job of their own, so the change and its follow-up commit together or not at all.
- **Jobs.** The work itself runs in the subscribing module's job, with the organisation of the job as tenant.
- **History rows as events.** Assessment writes every change of a reminder, finding or notice as a row in
  `assess.assess_event`; the row's id is the event's id. Notifications receives the notifiable ones in the same
  transaction into its inbox (`notify.pending_event`) and evaluates them per organisation
  ([ADR 038](adr/0038-notifications.md)).
- **Live events.** The browser receives changes over Server-Sent Events. The signal travels through PostgreSQL
  `LISTEN/NOTIFY`, so every `api` instance hears it; the stream holds no transaction open.

## The processing chain

Every step is an idempotent job. A state and the job that follows it are written in the same transaction.

| Step | Job | Started by |
|---|---|---|
| Fetch | `intel.sync-source` | `intel.schedule-due-sources`, when a source is due. One attempt: on failure the source's back-off decides the next run, which resumes at the last checkpoint. |
| Normalise | `intel.normalize-records` | new or changed raw records; one observation per raw record. Jobs of one source may run at once; each takes its records with `FOR UPDATE SKIP LOCKED`. |
| Merge | `intel.correlate-entry` | new observations or a changed signal class; the entry is recomputed from all its observations. Jobs that touch the same entry take turns: an advisory lock per primary key, taken before the entry is read. An entry whose primary key is no longer among the identifiers it is reached by is not taken over: it gives those identifiers up and is merged again from its own. |
| Announce | `intel.notify-entry-changed` | a material change of an entry, a minute later, so a wave of updates from several sources is assessed once |
| Forward search | `assess.match-entry` | an entry changed: which organisations and components carry its product keys |
| Read a repository | `assets.index-repository` | `assets.schedule-due-repositories`, a newly linked repository or «read now» |
| Reverse search | `assess.match-project` | a profile changed, by hand or by reading a repository |
| Assess | `assess.assess-alert` | a candidate in an organisation: findings, levels, reminders and notices from the rule set |
| Language model | `assess.estimate-alert` | optional, above a threshold and within quotas ([Rule set and levels](architecture/rule-set.md#language-model)) |
| Notify | `notify.evaluate` → `notify.deliver` | history rows that are events; rules, recipients, bundling, then sending |
| Digests, reminders | `notify.send-digest`, `notify.send-reminders`, `notify.send-overflow` | the schedule of a digest target or of the organisation's reminder rhythm |
| Warnings | `notify.distribute-warning` → `notify.receive-warning` | a warning without an identifier, for organisations with a rule for warnings |
| Catalogue | `catalog.grow` | unknown products in the sources ([ADR 040](adr/0040-catalogue-that-learns.md)) |

A system job that has to look across organisations only finds out *which* organisations are concerned, through a
narrow database function that returns identifiers, and queues one job per organisation
([Security model](security/security-model.md#tenant-isolation)).

## Jobs and schedules

The job system lives in `Ardea.Platform` behind `IJobQueue` (table `platform.job`).

| Concern | How |
|---|---|
| Picking up | `pending` jobs that are due, by priority and due time, with `FOR UPDATE SKIP LOCKED` |
| Lease | 30 seconds, renewed while the worker lives, with a token per pick-up that every later write shows; a watchdog releases expired leases. A separate timeout ends a job that runs too long, as a failed attempt. On shutdown a worker takes no new jobs, lets running ones finish for a grace period and hands the rest back. |
| Waking | `NOTIFY` when a job is queued; a slow poll as fallback |
| Retrying | exponential back-off with jitter; after the last attempt the job is `dead`, visible in the administration and retried by hand |
| Coalescing | at most one waiting job per coalesce key; a running or finished job does not block a new one |
| Schedules | `platform.schedule` with a cron expression and time zone for the instance's recurring work; one worker holds an advisory lock and queues what is due. When a source, a digest target or a reminder run is due is stored on its own row. |
| Clean-up | finished jobs after 7 days, dead and failed ones after 30 |

Jobs carry identifiers in their payload, never content, and the trace context, so one trace runs from the source to
the delivery.

## Unit of work and transactions

A unit of work is one transaction over every module it touches. The platform opens the connection and the
transaction, sets the organisation and the user in it (transaction-local, never per connection), and every module's
`DbContext` in the unit of work uses them.

| Case | Unit of work |
|---|---|
| Request | the whole request; the live-event stream reads in short transactions of its own |
| Job without outside contact | the whole job: state and follow-up jobs commit together or not at all |
| Job with outside contact (fetch, language model, sending) | three steps: read briefly, talk to the outside with no transaction open, then write the result and the follow-up jobs in one transaction |
| Fetch with checkpoints | each stretch up to the next checkpoint is a transaction of its own: raw records, cursor and follow-up jobs |

No transaction stays open across a call to the outside, and row locks, such as that of the per-organisation number
counter, are taken only in the writing step. Lease renewals use a connection of their own.

## Cross-cutting

| Topic | Rule |
|---|---|
| Identifiers | UUID version 7. Reminders and alerts also get a short running number per organisation for people. |
| Time | UTC in the database, `TimeProvider` in code; time zones only in display and schedules. |
| Errors | Expected failures are results up to the endpoint and become RFC 9457 problem details there; exceptions only for the unexpected. |
| Validation | At the API boundary; domain rules check again. |
| Configuration | Environment variables with the prefix `ARDEA_`, checked at start; a wrong configuration stops the process with a clear message ([Configuration](operations/configuration.md)). |
| Telemetry | OpenTelemetry to an endpoint the operator sets, nowhere else; logs never contain profile contents or secrets. |

## Extension points

| Extension | Interface | What it takes |
|---|---|---|
| Source | `ISourceProvider`, `ISignalProvider` in the provider SDK | an adapter class, with recorded real answers as tests ([Add a source](operations/add-a-source.md)) |
| Notification channel | `INotificationChannel` | a class and its settings |
| Language model provider | `IChatClient` (Microsoft.Extensions.AI) | configuration; no code for OpenAI-compatible endpoints |
| Version scheme | `IVersionScheme` | a class per scheme |
| Code platform | `IRepositoryHost`: branch head, SBOM, file tree, file | a class per platform; today GitHub and GitHub Enterprise Server |
| Lock file or platform file | a reader per file kind in `Assets` | a class with test cases from real files |
| Catalogue | JSON files in `data/catalog/`, one per vendor | an entry with its aliases, or none: the catalogue learns it |

## Scaling

- **More load in the worker:** start a second worker. Leases prevent double work, and a source that is queued has
  its due time moved past the fetch's timeout, so it is fetched once at a time. Rate limits per host apply per
  worker process.
- **More load in the API:** more `api` instances behind a load balancer; live events reach all of them through
  `LISTEN/NOTIFY`.

The module boundaries would allow a module to be moved out of the program, but nothing depends on it, and a message
broker is not part of the design.
