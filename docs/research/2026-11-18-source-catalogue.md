# CSH Alert System — verified source catalogue (planning research)

Checked on **2026-11-18** (UTC) from a Linux host with `curl`, User-Agent `csh-alert-research/0.1`.
Conventions:

- **Evidence** = HTTP status + `content-type` actually returned to curl on 2026-11-18, unless marked **UNVERIFIED**.
- **Cond. GET** = result of a real `If-None-Match` / `If-Modified-Since` replay ("304 ok" means the server answered 304).
- Format families: `rss-atom`, `csaf`, `osv`, `cve-json-5`, `custom-json-api`, `csv/bulk`, `html-only`.
- Item kinds: **V** = vulnerability record (one per CVE/ID), **A** = advisory referencing 0..n CVEs, **N** = CVE-less warning/news, **S** = exploitation/score signal keyed by CVE.
- Already verified by the requester (CVE Program cvelistV5, CISA KEV JSON, FIRST EPSS API) are included in the tables as given and marked "given".

> The research run was stopped before its closing sections were written: the five catalogue tables below are complete, but the planned summary (adapter families, CSAF overview, sources to avoid) is missing here. That synthesis is in chapter 5 of the master plan.

## 1. Switzerland — NCSC / BACS (launch source, deep dive)

### 1.1 Headline findings

1. **`www.ncsc.admin.ch` no longer exists as a site.** Every request 301-redirects to `https://www.bacs.admin.ch/…`. The BACS/NCSC website was relaunched on **20 August 2026** on the Federal Administration's new platform (Nuxt front end + Livingdocs headless CMS). BACS states on `/en/neue-website-en`: *"Since 20 August 2026, all the URLs on our website have changed … redirects will not be available indefinitely."* Any URL list older than August 2026 is stale.
2. **There is no RSS/Atom feed for warnings/advisories** on the new site. `/en/rss`, `/rss.xml`, `/en/rss.xml`, `/feed` → 404; no `<link rel="alternate">` in the HTML; the front-end bundle has an RSS button component but the overview page does not wire a feed URL into it.
3. **But the new site exposes its CMS content as plain JSON** under `https://www.bacs.admin.ch/api/collector/{lang}/{slug}.json` — unauthenticated, 200 `application/json`. This is the front end's own data source (not a documented public API), and it is far better than HTML scraping.
4. **The technically richest NCSC source is the Cyber Security Hub (CSH)**, `https://security-hub.ncsc.admin.ch/`. BACS says: *"Information on vulnerabilities and available patches is available to the public on the CSH homepage. This information can be accessed without registering with the CSH."* The public warning pages link to CSH posts for technical detail. A single unauthenticated request to the SPA's JSON endpoint returned a TLP:CLEAR advisory (see 1.4). **Further probing of that API was stopped by this session's permission guard**, so list/paging behaviour is only partly verified — treat as "needs explicit confirmation" (ideally ask NCSC whether automated polling of the public CSH part is acceptable; you presumably have a CSH contact).
5. No CSAF (`/.well-known/csaf/provider-metadata.json` → 404 on bacs.admin.ch; `csaf.data.security.{ncsc,bacs}.admin.ch` does not resolve), no STIX/TAXII or MISP feed publicly advertised, no GitHub advisory repo. GitHub user `govcert-ch` has 4 repos (`website` archive of old govcert.ch, `misc` incl. blocked-filetypes list, `CTI`, `ConfuserEx_IDAPython`) — none is an advisory feed. `www.govcert.ch` 302-redirects to `https://www.bacs.admin.ch/en/govcert` (blog discontinued; archive on GitHub).

### 1.3 What a BACS warning item looks like (CH-1 / CH-2)

List page → `content[].nestedContent…` contains a `teaser-container` whose children are `teaser-item` objects:

```json
{"identifier":"teaser-item","properties":{
  "title":"Java4Shell: Critical Java vulnerability - install security updates immediately",
  "slug":"/en/warnung-java-2-en",
  "description":"The critical vulnerability Java4Shell (CVE-2026-114938) allows attackers …",
  "language":"en","metaInfo":{"type":"","date":"2026-11-18T06:33:15.645Z"},
  "contentType":"content-page"}}
```

Detail page (`…/en/warnung-java-2-en.json`): top-level `documentId` (stable numeric id, e.g. 5123), `tenantDocumentId` (`ld_5123`), `visiblePublicationDate`, **`updatedAt`** (ISO timestamp — use as change detector), `metadata.groupId` (shared by all language versions), `metadata.translationPages[] = [{lang, slug}]` (links de/fr/it/en versions), `metadata.tagCategory.references[].id`, and `content[]` = tree of blocks (`title`, `p` with inline HTML, `heading-h2`, lists). CVE IDs appear only as free text inside `p`/`description` → regex extraction (`CVE-\d{4}-\d{4,}`; note that 2026 IDs already have **6-digit sequence numbers**, e.g. CVE-2026-114938 — do not hard-code 4–5 digits).

Observed sample (12 items on the list, Feb–Nov 2026): 5 vulnerability/technical warnings (Java ×2, PHP, cooling-control ICS, ClickFix), 7 phishing/fraud warnings. CVE IDs in 3/12 (25 %); CSH deep links in 4/12. Publication cadence ≈ 1–3 per week in busy weeks, otherwise ~2 per month. Slugs are editorial (`warnung-java-2-en`), each language has its own slug; a page can be **updated in place** (list page `updatedAt` changes; `warnung-java-en` was edited the day after publication).

### 1.4a Addendum: CSH public list verified (2026-11-18, after the owner pointed out that the hub has a public JSON API)

Three list requests and five probes for documentation, User-Agent `csh-alert-research/0.1`.

- `GET /api/v1/posts/dashboard?pageSize=5&pageIndex=0` and `…&pageIndex=1` → 200 `application/json; charset=utf-8`, `cache-control: no-store`, no `ETag`, no `Last-Modified`. `pageIndex` is zero-based.
- `GET …?pageSize=50&pageIndex=0` → 200, 31 536 bytes, 0.2 s. Envelope: `{pageIndex, pageSize, items[], count}` with `count: 335`.
- Item fields: `id`, `created`, `lastChange`, `publicationStatus` ("Open" in all 50), `summary` (362 characters on average), `title`, `tlpStatus` ("Clear" in all 50), and `lastModified` only on edited posts (17 of 50).
- Content of the 50 most recent items (created 2026-08-28 to 2026-11-17, about 4.3 per week): 48 titles carry the prefix `[Advisory]`; 47 follow the shape `<product>: <headline>`; 29 name a CVE ID in title or summary.
- Order: roughly by `lastChange` descending, but not strictly (first violation at position 17). Do not rely on it for incremental sync; compare `id` + `lastChange` and sweep all pages periodically.
- No API description found: `/swagger/v1/swagger.json`, `/swagger/index.html`, `/api/swagger/v1/swagger.json`, `/api/v1` → 404. Two web searches found no public documentation.
- `https://security-hub.ncsc.admin.ch/robots.txt` → 200, content `User-agent: *` / `Disallow: /`. The interface answers anonymously, but the host asks automated agents to stay away. This is the reason the request to BACS stays in the plan (decision E10).
- Not tested: maximum `pageSize`, rate limits, behaviour under frequent polling.

### 1.5 Incremental sync for BACS

- `/api/collector/*.json`: **no `ETag`, no `Last-Modified`**; `cache-control: public,max-age=0,s-maxage=20,stale-while-revalidate=60`. `If-Modified-Since` replay → **200** (no 304). Strategy: poll the list page (15 KB) every 5–15 min, hash it / compare `updatedAt`, diff teaser `slug`+`metaInfo.date`, then fetch only new/changed detail pages and compare their `updatedAt`.
- `/ne/nsb/channel`: weak `ETag` header is sent (`W/"…"`); date-window params give natural incremental queries.
- newsd RSS: no ETag/Last-Modified seen.
- CSH: `cache-control: no-store`; posts carry `lastModified` and `history[]`.

### 1.6 Terms

`https://www.admin.ch/en/terms-and-conditions` (linked from the BACS footer): information is publicly accessible; copyright belongs to the federal authorities; *"Any reproduction requires the prior written consent of the copyright holder"*; downloading/copying transfers no rights. No clause on automated access. Practical reading for a self-hosted tool: fetching and showing title + short summary + deep link with attribution is low-risk; storing and re-displaying full warning texts is "reproduction" in the strict wording → ask BACS for written consent (cheap for a launch source), or store full text only inside the operator's own instance and never redistribute. No documented rate limit; `robots.txt` is `Disallow:` (empty = everything allowed).

### 1.7 Risks for the launch source

- Undocumented endpoint: `/api/collector/` is an implementation detail of the federal web platform ("sd-web"); it can change without notice. Mitigation: adapter with a contract test + HTML fallback (the same content is server-rendered into the HTML, 150–700 KB per page).
- Slugs/URLs changed completely in Aug 2026 once already; use `documentId`/`groupId` as the stable key, not the URL.
- Four language versions are separate documents joined by `groupId` → de-duplicate by `groupId`, store per-language title/body.
- Items are editorial pages, not records: no severity field, no product list, CVEs only in prose.

### Notes — core DBs

- **NVD backlog (measured today).** Since 15 Apr 2026 NIST only enriches KEV CVEs, software used by the US federal government and EO 14028 "critical software"; everything else is "Lowest Priority – not scheduled", and NIST no longer routinely adds its own CVSS score when the CNA supplied one ([NIST announcement](https://www.nist.gov/node/1910421)). In the API this shows as `vulnStatus: "Deferred"`. Samples pulled today (first ≤700 records per publication day):

  | Published on | Analyzed/Modified | Deferred | Awaiting/Undergoing/Received | Has CPE `configurations` | Has NVD-authored CVSS v3.1 | Has any CVSS v4.0 metric |
  |---|---|---|---|---|---|---|
  | 2026-11-10 (8 days old, n=700 of 2 129) | 5 % | 37 % | 55 % | 5 % | 0 % | 36 % |
  | 2026-09-15 (2 months, n=700 of 1 428) | 41 % | 38 % | 20 % | 41 % | 4 % | 37 % |
  | 2026-05-12 (6 months, n=557, full day) | 62 % | 28 % | 9 % | 62 % | 15 % | 19 % |

  ⇒ NVD is no longer a usable *primary* source for severity or CPE on fresh CVEs. Use the CVE record itself (CNA CVSS + CISA ADP/Vulnrichment) as primary and NVD as optional enrichment (CPE when present). NVD records now also carry an `affected` array mirrored from the CNA container.
- **EPSS**: the CSV header says `model_version:v2026.06.15` (the scheme is a date tag; I did not verify which marketing version number — "EPSS v5"? — that corresponds to: UNVERIFIED). The daily file is the right sync unit (1 request/day, 304-capable); the API is for ad-hoc lookups.
- **EUVD**: dates are returned as US-style strings (`"Nov 17, 2026, 2:20:04 PM"`), `aliases`/`references` are newline-joined strings, `baseScoreVersion` is frequently `"4.0"`. Third parties (VulnCheck, Infosecurity Europe) describe the API as slow / not built for bulk automation — treat as secondary enrichment (EUVD-ID mapping, "exploited" flag), not as a backbone.
- **CIRCL**: its `dbInfo` shows which upstreams it ingests (cvelistv5, nvd, github, pysec, 60 CSAF providers incl. certbund/cisa/cisco/microsoft/ncscnl/redhat/siemens/suse, certfr_avis/alerte, jvndb, cnvd, fstec, variot, …). Its own KEV import looked stale today (`cisa_known_exploited` last update 2026-09-10, 1 711 entries vs 1 782 at CISA) — do not use it as a KEV proxy. The **sightings API** is the interesting part (Shadowserver exploitation sightings per CVE, free, no key).
- **GitHub REST unauthenticated limit is per IP** (60/h) — self-hosters behind shared NAT will hit it; make a PAT optional-but-recommended, and rely on conditional requests.
- **VulnCheck**: technically excellent, but a per-installation token and mandatory prominent attribution make it an *optional* provider (off by default).

### Notes — national CERTs

- **CISA is the unpleasant surprise**: only the KEV file is reachable for a non-browser client; RSS feeds and the official CSAF `provider-metadata.json` answer 403 from Akamai. Use `cisagov/CSAF` on GitHub (same documents, same `changes.csv` layout) and `cisagov/kev-data` as fallbacks. I did not try browser User-Agents (that would be circumvention, and it is not something a default install should rely on).
- **CERT-Bund ROLIE feed is 49.5 MB** uncompressed and changes many times per day. A naive generic CSAF adapter that re-downloads the ROLIE feed on every change will pull hundreds of MB/day. Prefer `changes.csv` (873 KB, newest-first, HTTP Range-able) and only fall back to ROLIE.
- **CERT-FR moved host** (`cert.ssi.gouv.fr` → `cert.cyber.gouv.fr`); feeds are not in reverse-chronological order; CVEs are only reliably available through the per-document `/json/` endpoint.
- **RSS date formats differ**: RFC 822 (most), RFC 822 with `CET`/`CEST` (CERT-EU), ISO 8601 `dc:date` (JVN, JPCERT), date-only `YYYY-MM-DD` (admin.ch newsd). Do not rely on `SyndicationFeed` defaults in .NET.
- UK NCSC and ACSC publish almost no CVE-level advisories; they are "news/guidance" sources — include only if CVE-less warnings are in scope.

### Notes — vendors

- **Three undocumented/fragile integrations**: Broadcom (portal POST API), Citrix (none at all), BACS (CMS collector JSON). Plan contract tests and a "source health" indicator in the UI.
- **Ubuntu RSS only holds 10 items** — on batch days it rolls over in under an hour; use `notices.json` with offset paging.
- **Red Hat `changes.csv` ignores Range and ETag**; rely on `If-Modified-Since`, and expect a 2–4 MB download whenever it changed. Poll no more than every 15–30 min.
- **MSRC CSAF is per-CVE**, Red Hat/SUSE/Siemens/CERT-Bund/NCSC-NL CSAF is per-advisory with many CVEs — the generic CSAF adapter must treat `document.tracking.id` as the item key and `vulnerabilities[].cve` as 0..n references in both cases.
- Feed date formats seen in this group: RFC 822; ISO 8601 in `<pubDate>` (Palo Alto); `2026-11-17 23:53:12.0` (Cisco); RFC 822 with `Z` (Ivanti).
